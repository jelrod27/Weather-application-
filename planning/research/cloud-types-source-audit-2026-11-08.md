# Scientific cloud types: source audit and decision

**Decision on 2026-11-08: no-go for a production scientific-name feature.** This completes the bounded research in [issue #666](https://github.com/jelrod27/Weather-application-/issues/666); it does not authorize implementation. Real DWD reports establish that some nearby stations explicitly report genera. The measured yield at the twelve predeclared points is too limited, the retained sample is too short, and meteorological/representativeness review is outstanding. Neither commercial candidate establishes an accessible, independently validated genus-classification contract. A separately approved, station-only research prototype is a possible next step; there are no launch-approved regions or genera.

## Evidence and reproduction

The companion directory [cloud-types-2026-11-08](./cloud-types-2026-11-08/) contains the predeclared coordinate/policy manifest, captured feed listing, immutable retrieval URLs and SHA-256 hashes, decoder failure log, compressed decoded reports, every evaluated slot, aggregates, representative original BUFR messages with provenance, mapping definitions, and content/evidence examples. Python gzip streams are JSON Lines, not application assets. The entire directory is approximately 0.5 MB; the roughly 17 MB input batch stays outside the repository. Attribution: **Contains modified Deutscher Wetterdienst data, 2026, CC BY 4.0; originating station/centre retained.** The modification is a decoded, geographically filtered projection and conservative mapping. [DWD terms](https://www.dwd.de/EN/service/legal_notice/legal_notice_node.html)

The rolling public directory will expire these files. Later exact full-batch re-decoding then requires an independently retained copy matching the committed hashes; it cannot be recreated from the listing or representative fixtures alone. Offline scoring and the original-message fixture checks remain reproducible from this repository. `retrieval-log.json` is committed and required for hash verification; a missing or corrupt log is an explicit error. `retrieve.py` records later per-file failures in its cache directory, exits nonzero if any file fails, and preserves the original audit logs. The commands above write decoded outputs only inside the disposable copy, preserving committed reports, decode summaries and metrics. It uses three workers and pauses after each download; this is a bounded batch, not a newly scheduled collector. [DWD current directory](https://opendata.dwd.de/weather/weather_reports/synoptic/international/)

The initial listing was retrieved after the manifest was written at the recorded UTC timestamps. Its 250 BUFR entries comprise 249 immutable batches plus one mutable `latest` alias; only immutable batches were downloaded. All 249 downloads succeeded: **16,980,410 bytes**, 10,218 BUFR messages, 84,260 declared subsets. The decoder retained 1,515 reports within 120 km of at least one declared point, including reports without genus fields. Twelve decoder failure events across eight batches and 7,020 decoded subsets without usable geometry remain recorded; neither is silently treated as success. The decoder stops the remainder of a batch after an unreadable message boundary; message/subset counts are counts reached by this parser, not a guarantee that every record in the bytes was recovered. A later prototype needs resilient framing/error recovery. These counts describe parsing, not meteorological accuracy. See [decode-summary.json](./cloud-types-2026-11-08/decode-summary.json) and [retrieval-log.json](./cloud-types-2026-11-08/retrieval-log.json).

The isolated run used Python 3.12.13, `eccodes` Python 2.45.0 and engine 2.50.0. BUFR master-table versions in the retained projection are 14, 18, 28, 31, 35 and 36. Source centre, subcentre, edition, local/master table versions, update sequence, station type, geometry/elevation, ranked cloud codes, vertical-significance fields, available quality/instrument fields and times are retained. Missing ecCodes sentinels become JSON null, never zero. The helper isolates a station subset, re-encodes it and reparses the bytes before extracting repeated cloud fields; cloning/extraction alone leaves old unpacked arrays and can mix stations. Tests compare extracted subsets with direct conditional access to the original multi-station message. [ECMWF subset example](https://github.com/ecmwf/eccodes/blob/676e9ce55bdbf8098cbf188d21cfa98bc10f165c/examples/python/bufr_subset.py)

## Sampling, all denominators and failure accounting

The manifest predeclared **12 coordinates** before decoding or scoring: San Ramon (37.7799, −121.9780), Hamburg (53.5511, 9.9937), London (51.5074, −0.1278), Athens (37.9838, 23.7275), Tromsø (69.6492, 18.9553), Nairobi (−1.2921, 36.8219), Kathmandu (27.7172, 85.3240), Tokyo (35.6762, 139.6503), Alice Springs (−23.6980, 133.8807), Manaus (−3.1190, −60.0217), La Paz (−16.4897, −68.1193), and Honolulu (21.3099, −157.8581). These deliberately span dense/sparse station geography, coasts, inland plains, high relief and remote oceanic conditions; they are not randomly selected or a global coverage estimate. Rounded selected-point elevations are declared **reference policy inputs**, not surveyed elevations or proof of terrain similarity. [Manifest](./cloud-types-2026-11-08/sampling-manifest.json)

Requested interval: **2026-11-01 20:00 through 2026-11-08 19:00 UTC inclusive**, 168 hourly slots × 12 = **2,016 slots per source/policy**. The captured listing retained only approximately one day of batches, beginning 2026-11-07 20:20:08 UTC. Accordingly, the complete-hour measurement window is **2026-11-07 21:00 through 2026-11-08 19:00 UTC**, 23 slots × 12 = **276**. The other **1,740 slots (86.31%) are retention-missing**. Some current batches carry much older late reports; those do not restore the missing historical feed/publication window. **This is not seven-day coverage or a representative week.** No long-running collection is required to complete this no-go research.

For each policy, eligible geometry is chosen independently of cloud-type success. At each query hour, use only reports with observation and feed-publication proxy at/before that hour, then choose the nearest reporting station and its latest observation. Missing genera at that station remain missing; the helper does not search farther until it finds an attractive genus. Missing elevation fails the proposed geometric policy. An absent in-range station is **unsupported under this sample/policy**, not proof that the location will never have data. Old reports are stale even if they name a genus. Batch failure can create missingness; it cannot remove query slots. Download/decode failure logs are separate process counts because failed records cannot truthfully be assigned to a particular station/time. Unparseable messages may change the outcome; this is a limitation of the measured yield, not a claim that all missing data are meteorological absences.

Baseline policy: age ≤90 minutes, distance ≤50 km, absolute difference from the declared reference elevation ≤300 m. These are proposed **application heuristics**, not source guarantees. All categories below are mutually exclusive: unresolved alternatives take precedence over explicit names; definite genera/alternatives take precedence over partial layer obscuration while retaining its codes; entirely obscured reports abstain; inconsistent clear/type or clear/positive-cover evidence is unclassified with no accepted genus. Mixed/optional semantics remain in the evidence record. [Helper and every slot](./cloud-types-2026-11-08/audit.py), [compressed slot data](./cloud-types-2026-11-08/slots.jsonl.gz)

### Freshness, daylight and policy sensitivity

Across 147 baseline slots with a selected report (including stale/missing-type reports), observation age is min 30, median 60, p90 360, p95 540, max 720 minutes. Selected distance is min 0.372, median 6.314, p90/p95 10.818, max 22.567 km. All seven explicit baseline results are 60 minutes old at their evaluated hour. Publication modification minus observation across all 1,515 retained reports has median 10.07, p90 17.07, p95 26.07 and max 6,362.03 minutes; that extreme is a very late old report. **This is a publication-delay proxy, not source receipt time or measured live end-to-end delivery latency.** Source receipt timestamps are unavailable; local retrieval completion is retained separately.

Unique within-station observation-time intervals have median/p90/p95 60 minutes, minimum 30, maximum 6,120 minutes. This is the observed interval distribution in a truncated feed, not a guaranteed station cadence. Retrospective file modification cannot establish first publication, intermediate outages, every correction arrival or cache delivery behavior. No production outage experiment occurred. [Machine-readable distributions](./cloud-types-2026-11-08/summary.json)

The shortened baseline spans 121 daytime, 14 twilight and 141 night slots. Explicit-genus counts are respectively 3, 1 and 3; ambiguous counts 1, 1 and 5. Solar-centre altitude is approximated using NOAA equations (day ≥0°, twilight −6° to 0°, night below −6°) solely to partition this sample. It excludes horizon/refraction and is not a sunrise product or a classifier validation result. [NOAA equations](https://gml.noaa.gov/grad/solcalc/solareqns.PDF)

Relaxing all three gates increases explicit availability to 5.43%, while allowing older/farther evidence and different station choices. Missingness can increase because a previously stale report without genus becomes a current missing-type result. Exploratory one-variable reruns, performed after the initial joint-policy scoring using only the predeclared bounds, isolate the effect here: raising age alone to 180 minutes produces the same 15 explicit / 7 ambiguous / 28 stale / 111 missing / 115 unsupported counts; changing distance alone to 25 or 100 km, or elevation difference alone to 200 or 500 m, leaves baseline category counts unchanged. [Sensitivity helper/results](./cloud-types-2026-11-08/sensitivity.py), [machine-readable sensitivity](./cloud-types-2026-11-08/sensitivity.json). Similar point elevations do not establish shared weather across coastal ranges, island relief or valleys; **terrain representativeness remains unvalidated**. A later prototype should extend these individual-gate checks to the chosen station cohort and apply named coast/mountain exclusions reviewed by a meteorologist rather than calling any threshold “accurate overhead.” For satellite evidence, propose age ≤30 minutes **after** product valid time/arrival semantics are verified, valid native footprint containment, acceptable viewing geometry and mandatory good-quality flags; exact thresholds and limb/night exclusions remain provider-specific blockers, not validated defaults.

## Conservative code/category mapping

Mapping version: `wmo-020012-conservative-v1-2026-11-08`. The exact applicable ecCodes tables for all six master versions in retained reports are captured with immutable upstream revision and hashes in [code-tables.json](./cloud-types-2026-11-08/code-tables.json). The original suggested EUMETSAT vocabulary URL failed retrieval (TLS/502); this audit uses the official ECMWF decoder's WMO-table definitions and the WMO Atlas, not an invented replacement specification. [Pinned table 31](https://github.com/ecmwf/eccodes/blob/676e9ce55bdbf8098cbf188d21cfa98bc10f165c/definitions/bufr/tables/0/wmo/31/codetables/20012.table), [WMO cloud identification](https://cloudatlas.wmo.int/en/cloud-identification-guide.html)

| BUFR 020012 raw code(s) | Accepted genus or evidence semantics |
|---|---|
| 0–9 | In order: Ci, Cc, Cs, Ac, As, Ns, Sc, St, Cu, Cb; an explicitly encoded genus. |
| 11–14; 17–18; 19 | Respectively Ci; Cs; Cc. Species/form detail does not change genus. |
| 15–16 | Cs is definite; Ci is optional. Never confirm both automatically. |
| 21; 23–29 | As; Ac. Code 27 may additionally involve As or Ns; these remain optional, not confirmed. |
| 22 | As **or** Ns; neither individually confirmed. |
| 31–32; 33; 34–35; 36; 39 | Cu; Cb; Sc; St; Cb. Other genera allowed “with or without” remain optional. |
| 37 | St or Cu, or both; unresolved alternatives. Clouds mentioned as usually above are not confirmed. |
| 38 | Cu **and** Sc explicitly; no dominance inferred. |
| 10 / 20 / 30 | Absence of the corresponding high/middle/low code group; one code alone does not establish a clear sky. All three can support a scoped no-cloud report. |
| 40–42; 44–49, where defined | Broad layer/phase/opacity categories, not genera; unclassified for the scientific-name objective. |
| 43, where defined | Source clear category, preserving source limitations; conflicting cloud codes or positive total cover force unclassified abstention. |
| 59–62 | Obscured/not visible, potentially just one layer; retain alongside other evidence. |
| 63, decoder missing sentinel, absent field | Missing, never clear. Reserved/unrecognized values abstain. |

Here Ci = Cirrus, Cc = Cirrocumulus, Cs = Cirrostratus, Ac = Altocumulus, As = Altostratus, Ns = Nimbostratus, Sc = Stratocumulus, St = Stratus, Cu = Cumulus and Cb = Cumulonimbus. Codes 15/16, 22, 27 and 37 deserve particular qualified review: obligatory, alternative and optional membership differ. The helper maps to **reported** genus, not a numerical confidence or an independently verified observation. A source's originating observation method is not reconstructed from cloud-cover values or a generic station name; station type/available fields are retained, while cloud-specific observing method and detailed quality are often unavailable.

For Meteomatics, keep 0/1 as source cloud-free land/sea categories, 2/3 as snow/ice surface categories with source limits; 4 and 9–12 retain the vendor's stratus/cirrus-labelled **satellite estimates**, not direct genus observations. Codes 5–8 and 13 are broad satellite categories, 14 unclassified. The transparent parameter combines clear and unclassified states into **−666**, so it cannot distinguish those outcomes; do not use it for a semantic clear-sky decision. No code is approved as a genus classifier here. For meteoblue, no category-value mapping is established; raw variable identifier 70 must never be mapped to a genus. [Meteomatics taxonomy](https://www.meteomatics.com/en/api/available-parameters/satellite/), [meteoblue variable listing](https://docs.meteoblue.com/en/weather-apis/maps-api/weather-model-domains)

Classifier acceptance thresholds were proposed in the manifest **before scoring**: independent time/location-matched precision ≥90% and recall ≥70% per supported class, at least 100 independent examples per class in each day/night regime, reported abstention/coverage and confusion matrices, plus qualified meteorological review. These are candidate product gates, not industry standards or achieved measurements. No candidate has qualifying independent matched evaluation here; **classifier accuracy stays unvalidated and blocks release**. Direct station reports need decoding/provenance and representativeness review, not a fabricated accuracy percentage. No synthetic case enters availability or accuracy metrics.

## Release gates and next task boundaries

**No-go now.** No source/region/genus combination is release approved by this audit. DWD establishes a technically usable **reported-nearby** semantics path for a limited set of real reports, but 7/276 explicit slots, only 23 measured hours, 12 decoder failure events, unresolved observing-method/terrain review and large unsupported geography do not justify a production launch. San Ramon specifically has no qualifying station under the sampled policies. Commercial category names, inaccessible contracts and missing independent evaluation cannot fill these gaps.

A later, explicitly approved station-only prototype task may: choose a small named station cohort independently of favorable weather outcomes; use existing authorized archives or a separately authorized collector for a stated observation window; test independent one-variable age/distance/elevation sensitivities; audit all missing, obscured, conflicting, malformed and delayed reports; request qualified mapping/observing-method/terrain review; and test whether users value clearly labeled nearby reports despite abstention. It must agree an operational availability target before assessing that cohort, preserve fallback copy and keep all prototype code outside production paths. This task is drafted here, not created or started.

A separate commercial clarification task may seek owner-approved access/quotes **only after authorization**: Meteomatics pixel/category/version/quality/rights and matched validation; meteoblue category-value semantics, model-versus-observation provenance, domain coverage, point extraction/Maps entitlement and caching/redistribution. No trial/purchase/contact is implied by this audit. Broad categories alone still fail the scientific-name objective.

Before any implementation: approve supported station regions/genera and wording; demonstrate current usable evidence and sustained availability with complete denominators; have qualified reviewers sign off faithful semantics and source-specific quality/terrain policy; resolve public-display/attribution/cache/retention rights and an all-in operating budget; validate any classifier independently against the predeclared per-class/day/night gates; accept the unsupported/ambiguous/stale/failure fallback; and separately authorize implementation/launch. **A positive future research result is not implementation approval.**
